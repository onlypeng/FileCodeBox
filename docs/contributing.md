# 参与贡献

本文档规定本项目的**代码注解规范**与**文档撰写规范**。

背景：本项目经历过一轮快速迭代，出现了典型问题——新写的模块有注解，早期的大文件
（`apps/base/views.py`、`core/storage.py`、`apps/admin/views.py`）几乎没有注解，
而 `readme_en.md` 等文档停留在旧版本，与实现严重脱节。文档一旦失真，比没有文档更糟：
读者会按错误的约定写代码、按错误的配置部署。

因此这两件事被写成本项目的硬性要求，而不是"建议"。

---

## 一、注解规范

### 总原则：注解写「为什么」，不写「做了什么」

代码本身已经说明了"做了什么"。重复它的注解不仅无信息量，还会**在被修改后变成谎言**。
注解真正稀缺的价值是解释那些**从代码里看不出来**的东西：

- 为什么这么做（而不是另一个显而易见的方案）
- 哪些坑已经踩过、不能改回去
- 边界条件、副作用、调用方必须满足的前提

### 1. 模块头 docstring：每个文件都要有

位置：文件最顶部（`from __future__` 之前）。用三引号，中文。

内容围绕三件事展开，顺序可以调整，但**必须回答"为什么"**：

1. **问题**：这个模块要解决什么真实问题（不是"提供 XX 功能"这种复述）
2. **方案**：关键设计选择是什么，为什么选它
3. **取舍**：刻意不做什么、以及不做的理由（这条最有价值，也最常被省略）

参考 `core/cluster.py`、`core/scan.py` 的模块头写法。

反例（不要这样写）：

```python
"""文件相关视图函数。"""   # 复述文件名，零信息量
```

正例：

```python
"""房间缓存：把房间内传过的文件暂存到服务端，让"离线也能取到"。

## 问题
直连快传是 P2P，双方必须同时在线。接收方晚一步进房间就永远拿不到文件。

## 方案
上传方把文件缓存到服务端，接收方上线后再拉取。缓存按房间隔离、按时间过期。

## 刻意不做
不缓存超过 roomCacheMaxSize 的文件——大文件缓存会打爆磁盘，
这类文件降级为纯 P2P，前端会明确提示"对方离线则取不到"。
"""
```

### 2. 函数 docstring：只写调用方需要知道、但看不出来的事

写这些：

- **边界条件**：越界值、空值、并发下的行为
- **副作用**：会写库吗？会发消息吗？会扣次数吗？
- **前提**：调用方必须先做什么（例如"调用前必须已校验权限"）
- **返回值的特殊约定**：例如"返回 None 表示 XX，而不是报错"

不写这些：

- 逐行复述实现
- 与参数名重复的废话（`code: 取件码` 这种，除非语义有陷阱）

### 3. 行内注释：只解释"非直觉"的地方

好的行内注释长这样：

```python
# 刻意不在这里删文件：秒传会让多条记录共享同一物理文件，
# 删掉会让另一条记录变成死链
```

```python
# 用 change() 而不是 os.rename：Windows 上跨盘 rename 会失败
```

坏的行内注释：

```python
# 遍历列表          <- 代码已经说了
# TODO: 优化        <- 没有上下文，没人知道要优化什么
```

### 4. 变更时的伴随要求

**改了逻辑，就必须改对应注解**。留下与实现矛盾的注解等同于埋雷。
Code Review 时这一条与代码正确性同等对待。

## 二、文档规范

### 1. 文档必须与实现一致

新增/修改接口、配置项、环境变量时，**同一提交内**必须同步文档：

| 改动位置 | 需同步的文档 |
|---------|------------|
| 新增/修改路由 | `docs/api/index.md` + `docs/en/api/index.md` |
| 新增配置项 | `core/settings.py:DEFAULT_CONFIG` → `docs/guide/configuration.md` + 英文版 |
| 新增环境变量 | `.env.example` → `docs/guide/getting-started.md` + 英文版 |
| 新增/修改模型字段 | `apps/base/models.py` 注解 + 对应迁移文件注解 |
| 部署形态相关 | `docs/guide/getting-started.md`（多实例、反向代理）+ 英文版 |
| 面向用户的新功能 | `readme.md`「功能一览」加一行，必要时补 `.github/images/` 截图 |

`readme.md` / `readme_en.md` 只保留功能清单、截图、快速开始与文档索引。
**细节一律写进 `docs/`**，不要往 README 里堆配置表和接口表——两处维护必然失真。

### 2. 中英文文档同步

`readme.md`（中文）与 `readme_en.md`（英文）、`docs/guide/*` 与 `docs/en/guide/*`
必须覆盖**同一组功能**。历史上英文版停留在旧版本、缺少收件箱与直连快传章节，
这类滞后对国际用户是直接的误导。

### 3. 文档里不写没验证过的东西

命令、配置值、接口返回示例，写进文档前必须实际跑过一次。
本项目踩过的坑：readme 曾建议 `WORKERS` 设为 CPU 核数，但当时房间 WebSocket 状态
在进程内存里，照着配必然出现"房间消息只有一半人收到"，且极难排查。

### 4. 版本与日期

涉及版本兼容性的说明，注明适用版本或日期，避免后来者误判。

## 三、验证要求

改动即使"只是注解"，也**不能只靠肉眼**。注解写错位置会破坏字符串、缩进或语法。

### 后端

```bash
# 1. 语法与导入（py_compile 查不出缺失 import，必须真实导入）
python -c "import apps.base.views, core.storage, main"

# 2. 全量测试
pytest -q
```

### 前端

```bash
npm run type-check   # vue-tsc
npm run build        # typecheck 通过 ≠ 能构建，必须真的 build
```

> 注意：`vue-tsc` 与 `@vue/compiler-sfc` 检查的规则集不同。
> `<script setup>` 里写 `export` 时 typecheck 完全不报错，只有 build 会失败。

### 文档

```bash
cd docs && npm run docs:build   # 确保 vitepress 能构建（链接失效会报错）
```

## 四、提交规范

- 格式：`type(scope): 简短说明`
- type：`feat` / `fix` / `docs` / `refactor` / `perf` / `test` / `chore`
- 正文说明**为什么改**，尤其是取舍与踩过的坑；这类信息在代码里放不下，
  但半年后排查问题时最有用
- 注解/文档类改动单独提交，不要与逻辑改动混在一起（便于 review 与回溯）
